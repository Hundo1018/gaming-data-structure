## Report: baselines

### Summary

This repo has no third-party library dependency today. The libraries a reviewer would expect as baselines, or that a later round of candidates might reuse, mostly do not have a first-party C API: EnTT, gaia-ecs, EntityX, nanoflann, Boost.Geometry, CGAL, PhysX, Bullet's btDbvt, Jolt, ReactPhysics3D and Godot's DynamicBVH are C++ only. The ones that do have one are flecs (a C99 core), libspatialindex (sidx_api.h), Embree (a C99 API), Box2D v3 (written in C17), Chipmunk2D (C99), FLANN, ODE and pico_ecs (C11). Each of these can be hosted in either harness at about the same cost. The rest are not usable as candidates in either language, for reasons that have nothing to do with C or C++: Unity Entities and Arch are C#, Bevy, hecs and Parry are Rust, Unreal Mass is tied to the engine and its EULA, CGAL is GPL v3+, DualSPHysics is LGPL and built into its solver, Box2D and Chipmunk are 2D only, and Jolt's broadphase depends on its BodyManager. Hosting a C++ library in the C11 harness costs four concrete things, all measured here. First, a build change: the CMake project is C only and the glob picks up only structure.c. Second, a link dependency on libstdc++. Third, every contract operation becomes a real call instruction unless both translation units are built with -flto. Fourth, the wrapper must catch(...) at the boundary, because some libraries throw (nanoflann does) and GCC compiles C without -fexceptions; libspatialindex's own C API does exactly this, with 188 catch clauses. Allocation counting keeps working: libstdc++'s operator new calls malloc@plt and its aligned form calls posix_memalign@plt, and a C malloc interposer counted all 12 allocations made by a C++ wrapper. The larger adaptation costs come from the contract, and they are the same in both languages: the accept test must be gds_dist2 and k-nearest results must be ordered by (dist2, id), libraries rarely offer a move operation, and none offers rewind that discards later history. In the other direction, how a discovered structure gets consumed favours C. Unity/Burst, Rust/Bevy, Python and Zig all bind through the C ABI. The Rust Nomicon says Rust cannot call a C++ library directly, and bindgen cannot bind inline or template C++. Jolt and PhysX both gained third-party C wrappers so that other languages could use them. C++ engines are mixed: Unreal compiles C++20 by default, so the old C++20 candidates would drop in; Godot is C++17 with exceptions off, so the C++ tree's std::bit_cast and concepts would need shims. The current C11 headers are not valid C++ (0 of 18 compile), but only three constructs block them.

7. **[neither, measured]** The largest adaptation costs come from the contract and are the same in C and C++. 11. **[C, measured]** Non-C++ consumers bind through the C ABI, so C is the easier interface to export. Rust cannot call C++ directly, and bindgen cannot bind inline or template C++, which rules out header-only template libraries in the EnTT and nanoflann style. Jolt (four separate third-party C bindings), PhysX (physx-sys generates its own C wrapper) and flecs (all listed bindings go through its C API) show the ecosystem routing around C++.
   - evidence: https://doc.rust-lang.org/nomicon/ffi.html: 'Rust is currently unable to call directly into a C++ library'. https://rust-lang.github.io/rust-bindgen/cpp.html lists as unsupported 'Inline functions and methods' and 'Template functions, methods of template classes', and says exceptions 'will generate undefined behaviour'. physx-rs physx-sys/README.md:84 'Since C++ does not have a standardized and stable ABI ... physx-sys generates ... a plain C wrapper'. Unity https://docs.unity3d.com/Manual/ios-native-plugin-create.html: 'If you use C++ ... declare functions with C linkage to avoid name mangling'; 'C or Objective-C plug-ins don't require C linkage'.

14. **[C, inferred]** Neither tree's candidates can be called through FFI as they stand, because both are header code (static inline functions, or templates and concepts). Exporting a C candidate needs a trivial .c file of non-static forwarders, or bindgen's --wrap-static-fns, and adds no runtime. Exporting a C++ candidate needs an extern "C" wrapper TU and brings libstdc++ into the consumer's link.
   - evidence: Contract is static inline: gds/api.h:7-11, gds/spatial/api.h:7-12. bindgen --wrap-static-fns generates a C file of wrappers for static inline functions: https://lkml.rescloud.iu.edu/2411.0/07592.html and the Android Soong commit https://gerrit.omnirom.org/plugins/gitiles/android_build_soong/+/810c37ec1e0fa218979ca8b0cc72db68b477cfb9%5E%21. libstdc++ NEEDED: toy readelf above. The forwarder-file effort is inferred; I did not build one.
15. **[neither, measured]** Unity/Burst can call native code only through primitives, pointers and handle structs, never structs by value. The suite's spatial contract passes Vec3 by value, so an export callable from Burst would need pointer parameters. This applies to C and C++ alike.
   - evidence: https://docs.unity3d.com/Packages/com.unity.burst@1.8/manual/csharp-burst-intrinsics-dllimport.html: 'Passing structs by value isn't supported; you need to pass them through a pointer or reference.' substrate/include/gds/spatial/api.h:72-76 (insert, move_by, query_radius and query_knn take Vec3 by value).
16. **[neither, measured]** Rollback consumers treat game state as opaque snapshots. GGPO is a C++ implementation behind a C API with save/load byte-buffer callbacks, and bevy_ggrs snapshots registered components. Engines today do what rebuild_rewind models, and they consume rollback through a C-shaped interface.
   - evidence: pond3r/ggpo src/include/ggponet.h:12 extern "C", :210 save_game_state, :219 load_game_state; LICENSE is MIT. gschup/bevy_ggrs README.md:8 ('snapshotting only the components and resources you register'). substrate/include/gds/spatial/rebuild_rewind.inc.h:1-9.
17. **[C, measured]** Box2D's move from C++ (v2.4) to C17 (v3) is a precedent from game physics: a dynamic AABB tree with a per-operation C API. Its author gives productivity and compile speed as the reasons, not bindings.
   - evidence: Tag v2.4.2 README.md:41 'Highly portable C++', b2_dynamic_tree.h:78,81,87,102 (CreateProxy/DestroyProxy/MoveProxy/Query). HEAD collision.h:794,797,800,814 (b2CreateTreeProxy, b2DestroyTreeProxy, b2DynamicTree_MoveProxy, b2DynamicTree_Query with callback). https://box2d.org/posts/2024/08/releasing-box2d-3.0/: 'C lets me focus on algorithms and data structures', 'C compiles very fast', and 'MSVC is behind the current C standard'.

## Report: shim

### Summary

Calling the real C++ class gds::candidates::Soa from the C11 harness through a 15-function extern "C" shim works. All 11 builds I made (the shim with gcc and no LTO, with gcc -flto, with clang -flto=thin, plus controls) give the same results as cpp-bin/gds_ecs_soa on all 12 ECS workloads in verify and bench mode, with 0 strict and 0 soft differences. Without LTO the boundary costs 14.9 instructions per contract call against the inlined C soa on w06_point_narrow, which is 4.67M calls per repetition: 146.6 vs 131.7 Ir/op, 1.113x the C baseline and 1.070x the C++ binary. Most of that is not about C++: the same C soa compiled as a separate C file behind the identical extern boundary costs 11.6 Ir per call (1.088x), so C++ adds about 3.3. LTO removes the cost. With gcc -flto, 12 of the 15 wrappers are inlined and only create, destroy and construct stay out-of-line calls. With clang -flto=thin, all 15 wrappers are inlined and the harness calls Soa's own create/destroy/query directly. Point-access workloads then come out below the C baseline (0.974x gcc, 0.969x clang), because the two soa implementations compile slightly differently, not because of the boundary. On the query-dominated workloads (w04, w02) the boundary is crossed only once per query or operation, and the gcc variants all land within ±1.5% of each other (b and c within 1.1%); the differences track where the query loop gets compiled, not the call cost. The clang figures there (0.82x to 1.19x) depend on whether clang inlines the digest function into the query loop. On allocations: yes, the C allocator counts a C++ library's allocations. libstdc++'s operator new calls malloc@plt, which binds to the harness's exported malloc, and peak_bytes, alloc_count and reported_bytes match the C++ binary exactly on all 12 workloads. The flip side for the decision: a C harness that uses a C++ library needs libstdc++.so.6 at run time again, plus a hand-written wrapper (134 lines here for one 171-line class) and LTO built with one compiler family to avoid the per-call cost.

Logs: lang-shim/equiv/all.log and all2.log.
2. **[depends, measured]** Without LTO (gcc 13.3), calling the C++ Soa through the C ABI costs +14.93 Ir per contract call against the inlined C soa, and +9.53 against the C++ binary. The C soa compiled as its own C11 file behind the identical extern boundary (control e) costs +11.62 Ir per call on w06 (1.088x a) and +11.46 on the non-query part of w04. The C++ code adds only about 3.3 Ir per call on top (b vs e: 1.023x).

4. **[neither, measured]** gcc -flto on every file and at link removes the boundary cost. On w06, c is 128.2 Ir/op (0.974x a, 0.935x C++). On w04 the non-query part is 117.39 Ir/op (-3.4 vs a). As a control, LTO on the pure C soa changes nothing (a_lto - a = -4,592 Ir out of 615M on w06), because the single-file C candidate was already fully inlined.
   - evidence: cachegrind as above: v_c w06 598,657,498 Ir/rep, v_a_lto 614,924,202, v_a 614,928,794. Build: lang-shim/build.sh v_c shim gcc lto novx512 (gcc-ar archive, -flto at compile and link; commands in v_c/build.log).
5. **[neither, measured]** Inlining under gcc -flto (c): 12 of the 15 shim functions disappear. Only soa_shim_cxx_construct, soa_shim_cxx_create and soa_shim_cxx_destroy remain. soa_shim_replay_apply calls soa_shim_cxx_create and tail-jumps to soa_shim_cxx_destroy; get, set, add, remove, alive, mask, query, integrate, sync, entity_count, reported_bytes and destruct are inlined into the harness, and no Soa:: method symbol remains except ~Soa. For comparison, the C++ binary also keeps Soa::create out of line from Replay::apply. Without LTO (b), every contract operation is a call or tail jump to soa_shim_cxx_*, and create and query take a second call into Soa::create and Soa::query.

6. **[neither, measured]** Inlining under clang 18.1.3 -flto=thin with lld (d): the harness makes no call or jump to any soa_shim_cxx_* function, so all 15 wrappers are inlined. The harness calls the C++ methods directly instead: Soa::create and Soa::destroy from soa_shim_replay_apply, Soa::query from soa_shim_replay_end_of_frame, ~Soa from run_one_repetition. 7. **[neither, measured]** On the query-dominated workloads the boundary does not matter. The query loop runs inside one call per frame: 99.7% of w02's instructions and 93% of w04's are in the query and integrate loops. The gcc variants all fall within ±1.5% of a (b and c within 1.1%), and the spread follows where the loop is compiled: Soa::query out of line in b = 7.194G on w04, inlined into end_of_frame via LTO in c = 7.234G, a = 7.170G. That is why c is 1.008x a on w02 even though LTO removed every per-call cost.
   - evidence: python3 lang-shim/perfn.py <v> w04_random_access / w02_query_heavy, giving function-level Ir(r2)-Ir(r1). Totals per repetition on w02: v_a 10,303,466,050, v_b 10,323,520,743, v_c 10,381,730,126.

### Summary

The two languages mix cheaply in the direction that matters. All 549 (g++) / 544 (clang++) errors from compiling the 22 C translation units as C++20 have four causes: void*-to-T* conversions (508), C99 `restrict`, and, under g++ only, `_Static_assert` and `_Alignas`. Designated or compound initialisers, the anonymous GDS_VEC structs, `__attribute__`, the builtins and the asm barrier caused none. Adding extern "C" guards, typed casts and `static_assert` to 14 substrate headers (+59/-20 lines, plus +15/-2 in CMakeLists.txt) lets soa and uniform_grid compile as C++20 with no change to their own code. A further 5 files (+24/-15) bring all 21 candidates and the floor tool to 0 errors as C11 and as C++20 under gcc, clang, g++ and clang++. The C object code stays byte-identical: 28 of 28 objects disassemble the same. With every candidate compiled as C++ against the C substrate, verify mode reproduces all 263 cpp-bin results under both g++ and clang++. Instructions executed change by at most 0.46% (gcc) and 0.008% (clang). One real cost of mixing: in C++ the contract's redeclaration check no longer catches every wrong signature. A candidate whose create() drops a const builds and links silently, but a decltype-based static_assert restores the check (tested). On portability the C build is weaker: its allocator forwards to glibc's `__libc_*` entry points, which musl marks hidden and lacks `__libc_memalign` entirely (link fails both dynamically and statically, tested), and which macOS libmalloc/Libc do not have (0 hits). The C++ build's operator new replacement, by contrast, is sanctioned by the C++ standard and supported by libc++ on Mach-O and ELF. That gap can be closed in C for about 85 changed lines with no measured loss today. Across 263 bench runs, 0 of 7,518,569 measured-window allocations came from outside the executable, and a wrapper-based allocator matched interposition on all 526 checksum and memory comparisons and links against musl. However, wrappers count 0 of the 106 allocations a C++ std:: container test makes, where interposition counts all 106. So a hybrid built on wrappers would also need the C++ build's operator new forwarding. The clang C build has 0 warnings and matches cpp-bin on 263 of 263 verify runs and the gcc C build on 263 of 263 bench memory fields.

## Report: codegen

### Summary

With the same GCC 13.3 and the same flags, C and C++ produce near-identical instruction counts for the same algorithms. I measured 42 candidate x workload pairs as Ir(--repeats 2) minus Ir(--repeats 1). 29 of the 42 fall inside 0.97..1.03. The geometric mean of C/C++ is 1.0076 for ECS (20 pairs), 0.9585 for spatial (22) and 0.9816 overall; summed over all pairs it is 0.9943. Every ratio outside the band traces to a specific code shape, and none of them is a property of either language. (1) In grouped_sparse_set, GCC's inliner did not inline gds_digest_entity at the query_set_ call site in C, but did in C++. Forcing it inline in C (E3) puts C 1% below C++ on w02 and 10% below on w04. (2) The C ECS oracle (`reference`) is a hand-written bucket-array hash table that it scans bucket by bucket; the C++ one was std::unordered_map, iterated along its node list. That is a change in representation, not in codegen. (3) The C++ k-nearest search passes the free function `nearer` to std::partial_sort and the heap functions as a function pointer, so every comparison is an out-of-line call; the C port's macro sort template inlines the comparison. (4) The C++ oracle fills its kNN candidate list with std::vector::push_back, which costs 35 instructions per element against 23 for the C plain-array store. Changing (3) and (4) in a scratch copy of the C++ (E1, E2) brings brute_force from 0.906 to 0.986 and lifts the spatial geometric mean from 0.9585 to 0.9708. (5) On hs01, four spatial candidates are 6-9% cheaper in C. The cost is all in move_by, where C++ keeps one out-of-line helper call per move (163 vs 193 straight-line instructions per move for spatial_hash). Forcing those helpers inline (E4) only moved the call up one level and did not close the gap, so that residual is located but not fully explained. The measured binaries are rebuilds with -mno-avx512f added to both languages, because valgrind 3.22 crashes on the shipped AVX-512 binaries. The rebuilt binaries return the same checksums as the shipped ones on all four shortened workloads; the shipped binaries' own instruction counts could not be measured here. For the C-vs-C++ decision, my part shows neither language has a codegen advantage that survives a small source change on the other side. The spread between languages (0.85-1.11) is as large as many differences between candidates, so C and C++ measurements must not be mixed in one ranking.

### Caveats

1. Not the shipped binaries. What I measured are rebuilds of the same sources with the same flags plus -mno-avx512f, applied to both languages. Valgrind 3.22 raises SIGILL on the shipped -march=native (sapphirerapids) binaries, and this VM has no hardware counters, so the shipped binaries' instruction counts could not be determined. Shipped hot functions do contain EVEX instructions (vrndscaless, zmm stores), so their counts may differ somewhat from the AVX2 rebuilds.
2. Shortened workloads. I cut only frames/ticks (w02 to 40, w04 to 60, s01 to 20, hs01 to 31) and kept the populations, so the load step weighs more than in full runs. Ratios for the full-length workloads were not measured.
3. What r2 - r1 contains. It is the cost of the second repetition, which starts with the allocator state left by the first (for C++ reference, 1,881.2M vs 1,865.4M for the first repetition alone under callgrind toggle). It also includes a few thousand Ir of report work whose sorting depends on timing. Run-to-run variation is at most 3,058 Ir per process, at most 10 ppm per repetition.
4. Attribution limits. The per-operation split uses DWARF inline chains (addr2line -i). Totals are exact: the attributed sum equals the profile total in every case. GCC tail-merging can, however, charge shared instructions to one inline site; for example the C++ delta_grid 'remove' on s01 is really move_by code.
5. Two residuals are located but not explained. The +45.8M on the reference digest lines, and the remaining 6-9% in move_by for the four hs01 candidates after E4, are pinned down but their cause is not identified below that level.
6. Scope of the experiments. E1-E4 are diagnostic edits to scratch copies, not proposals. E2 replaces std::vector with std::unique_ptr<T[]> in the oracle.
7. One compiler only. Everything here is GCC 13.3 on x86-64; Clang may make different inlining decisions.
8. The language versions are not literally the same code. The two harnesses differ (chrono vs gds_now_ns, vector vs plain arrays, operator new replacement vs malloc replacement), and the ECS oracle's representation was changed by the port.
9. Instruction count says nothing about time. It cannot rank the builds by wall clock: cache behaviour, branch prediction and instruction latency are not in it.
10. Nothing was changed in /home/user/gaming-data-structure (git status clean, HEAD a6804f7) or in cpp-src. All builds, workloads and variants are in my scratch directory.

## Report: authoring

### Summary

The record of the port says C cost real work. It does not show that C made the porting agents produce wrong code. Candidates grew from 4,429 to 5,239 non-blank lines (1.18x; 1.20x with comments stripped) and the substrate grew 1.36x. The spatial candidates, which used lambdas, templates and std::sort, grew most (1.17x to 1.43x); the ECS candidates grew 1.05x to 1.15x. Replacing the C++ constructs took 186 #defines (the C++ has 2), seven template headers (1,138 lines), a re-implementation of std::vector growth and of libstdc++'s introsort, and one-off workarounds (listed below). All 8 porting agents' equivalence runs showed 0 differing checksums. The only compiler diagnostic in their build output was one -Wattributes warning (inline plus noinline). The three real defects were all in substrate and exemplar code the orchestrating session wrote, not in the porters' code, and all three are error classes C makes easier: two float maxima written in the wrong operand order (they differ from std::max only on NaN), and gds_vec_push reading its argument after freeing it. The same aliasing class is still present in gds_vec_assign; my probe shows ASan heap-use-after-free for the pointer form, and a silently wrong value for the macro-text form, which no sanitizer reports. Going the other way, the C made several hidden C++ costs explicit (vector copies per tick in the rewind wrapper, `inner_ = S(cfg_)` charging two indexes at peak, per-query temporary vectors). None of them was a defect: allocation counts matched exactly. Of 45 review findings from the earlier C++ authoring round, only one involved a C++ language construct (a const_cast). On contract checking, the C prototype redeclaration rejects a `uint32_t salt` that the C++ concept accepts silently, and in C++ only the run-time oracle caught it. An exact-type static_assert in C++ catches it too, so that gap is in how the concept was written, not in the language. These are ports from a C++ reference with a 12-rule prompt; the record cannot show what writing a new candidate in C from scratch would cost.

### Caveats

1. Every Ir figure comes from the -mno-avx512f twins, because valgrind 3.22 cannot decode the shipped AVX-512 binaries. My CMake twins are byte-identical to the shim and codegen twins (cmp, 23 of 23 binaries), so rows 2 and 4 re-measure the same binaries rather than independent builds. The exceptions are my no-LTO shim and my C control, whose link order differs. My LTO shim is byte-identical to theirs yet read 10,061 Ir (17 ppm) away, which is above codegen's stated 10 ppm noise and irrelevant to any conclusion.
2. Ir is not time. The machine has no hardware counters, and no wall-clock timing was taken or used.
3. Codegen was re-checked on 6 of 42 pairs, plus full-length runs of 2 of them. Static libstdc++ was tested on soa only (the C++ soa and the shim), on this glibc 2.39 host. I did not run a static binary on an older glibc, and the C++ build still requires GLIBC_2.38.
4. ASan was tested with GCC 13.3 and libasan.so.8 only, on soa and the w05 workload; clang's ASan was not tested. That the C interposer defeats ASan on every candidate is inferred from the mechanism: the executable's malloc preempts the sanitizer's.
5. Compile cost covers two candidate TUs. It includes the gcc driver, cc1/cc1plus and the assembler; it does not include linking or the substrate TUs, and it is not a timing of the whole build.
6. Third-party checks used the commit SHAs in lang-baselines/heads.txt, so they confirm the citations as written, not whether HEAD has moved since. The web pages were fetched today, 2026-10-09. I did not check the Unity licence, Mass/EULA, CGAL, DualSPHysics, ODE or Parry rows.
7. The finding that a 1.2x prediction bound sits between the languages' instruction ratios is a proxy: predictions are judged on step_ns_p50, not Ir.
8. Not re-checked: hybrid's 549/544 error classification, its contract-overload test, its macOS source greps, and its 263-run allocation trace; authoring's journal-derived counts and contract-break logs; baselines' toy LTO and exception findings beyond what is listed.
9. Nothing in /home/user/gaming-data-structure (HEAD a6804f7) or in cpp-src (83a58a6) was modified; git status is clean in both.
